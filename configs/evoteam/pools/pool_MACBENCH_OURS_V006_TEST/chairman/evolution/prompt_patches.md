- Budget-gated orchestration: treat wall-clock/cost as a hard constraint, not a soft one. (1) Cap initial reconnaissance at ~5 tool calls (list_tools, then describe only the 1-3 tools you will actually call) and send the first dispatch within the first ~10-15% of the wall-clock budget using whatever context you have; never refine a plan while teammates idle. (2) Dispatch all needed agents in ONE batch of messages, each containing full scope, input data, expected deliverable format, read/write boundary, and a self-check command — so no round-trip is needed for clarification. (3) Schedule mandatory checkpoints at 50% and 70% of the budget: at 50% require partial results from every agent; at 70% freeze all writes, verify what exists, and submit. A submitted partial answer always beats a terminated run with no output. (4) If a sub-analysis has produced no intermediate artifact after ~2 attempts, drop it, mark it unresolved, and finalize with the verified remainder.
- Own the critical path: when a single artifact (largest file, most-tested module, the one input everything else imports) gates the whole deliverable, implement it yourself first, or delegate it only with a hard time box plus an early intermediate artifact (skeleton written + first passing check) — and take it over the moment that artifact is late. Never spend more than a short interval waiting on a delegate for the gating artifact while other work is blocked on it.
- Split large file writes into chunks of at most ~200 lines per tool call (append with a quoted heredoc) and syntax-check each chunk immediately; a single oversized write can be rejected outright and waste the whole attempt. Write primitives first, then the domain object, then builders, then public entry points.
- When validation code must satisfy tests that match exception messages with regexes, check that the required words appear in the expected ORDER in the message (search semantics, not set-of-words), and that helper errors quote Python types verbatim when tests assert on type names. Also verify order-dependent details like sorted outputs, and that empty/zero inputs take the expected branch (e.g. empty list disables a feature instead of raising a 'none found' error).
- Verify produced artifacts, not only unit tests: write a throwaway script that builds the real outputs and recomputes every claimed invariant from bytes (manifest hashes/sizes, permission bits, timestamps/reproducibility under an epoch variable, resource placement) plus an end-to-end round trip (build, unpack, rebuild, import). If a stricter sibling test suite cannot be imported because dependencies are missing, emulate its assertions through the low-level API rather than skipping verification.
- When reconstructing library/module code from memory rather than from a reference copy, never add defensive guard clauses, extra type checks, or validation branches that no test or caller requires. Guards and error paths are precisely where remembered behavior diverges from real behavior: implement the permissive merge/no-op path (accept the input, merge the options) and let the test suite reveal which rejections are actually mandated.
- Two rules for programmatic source patching and for self-written verification scripts: (a) after patching code by regex/text replacement (dedent+indent, body insertion), read the emitted region back and inspect its indentation and scoping before running anything — a successful syntax parse does NOT prove the block landed at the right nesting level, because a wrongly-dedented body can still parse as valid but different code; (b) when asserting behavior of a library whose output representation you are not certain of, probe the real values first (print, do not assert) for 2-3 primitives, then assert only observed values or representation-independent invariants (round-trip equality, types, key sets). Guessed representations produce false failures that look like implementation bugs and burn iterations on your own script.
- When adding or changing any read/write API serializer (especially nested/embedded objects), assert round-trip self-consistency as a first-class check: fetch a record, send the exact retrieved representation back with PUT, and also PATCH only the nested keys — all must return 2xx. A read representation that the write path rejects (e.g. empty-list values, null-vs-absent, forced-normalised fields) makes whole-object clients fail even though scalar-only edits work, and it will not show up in create-only tests.
- Before assigning people or resources to records in any replanning/migration task, read the pre-existing baseline records first: provisional or draft rows usually already encode the intended assignment. Preserve each existing assignment unless a documented constraint forces that specific change, and derive all derived obligations (guarantees, penalties, notice fees) from the preserved map — gratuitous reshuffling silently re-attributes those obligations even when the total stays the same.
- Before any bulk write to a live system, spend one throwaway call probing the state machine: can an already-committed/submitted record be edited, and does cancel-then-remove actually work? Discovering afterwards that committed records are immutable forces cancel+recreate+re-commit repairs (~3-4x cost) and leaves cancelled residue that can pollute "active count" checks, so learn the lifecycle on one record while the fix is still free.
- Before starting analysis on any task whose deliverable is "one record/arrangement per entity" (per child, per family, per order, per event), count the required write units first and measure the per-write cost with ONE probe write early. Then decide explicitly whether full completion is affordable; if it is not, move the mechanical write stream to the front of the schedule (run it in parallel with analysis) instead of doing all the cheap analysis first and leaving the expensive, uncompressible work for the end. Each native write typically echoes a large object, so N writes can cost an order of magnitude more context than the analysis that designs them — measure at n=1, not at n=90.
