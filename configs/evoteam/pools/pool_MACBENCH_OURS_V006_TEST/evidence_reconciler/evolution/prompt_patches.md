- When gathering evidence from a data source, prioritize breadth over depth under time pressure: pull the core/aggregate records first (the few that answer the assigned question), report partial findings immediately, and only chase edge cases if explicitly asked. Exhaustively inspecting every record consumes the whole budget and starves downstream work.
- Batch all independent read-only tool calls into a single parallel block instead of issuing them one at a time; each sequential round-trip multiplies wall-clock cost, and under a fixed time budget that directly causes termination.
- Read the project's own instruction/manifest file (task description, README, or any build/check script it references) in the FIRST batch, before exploring source. It names the official build and test commands and the scope boundaries; guessing a runner or discovering the sanctioned command late wastes both calls and setup effort.
- A verification harness must compare raised exceptions and returned values on SEPARATE code paths (catch, then compare type/message; else compare value). Never fold both into one sentinel tuple, because any mismatch between the sentinel's shape and the real exception payload fabricates failures that then have to be re-diagnosed as if they were real bugs.
- Before declaring a deliverable final, re-read the list of gaps you yourself flagged; either close them or label the report explicitly as partial. Sending a 'final' report that still has open items forces a corrective follow-up and makes the recipient distrust the headline.
- Before telling anyone their number is wrong, first reproduce that number from the inputs THEY stated (scope, attribute, and any reassignment they made). If you cannot reproduce it, the discrepancy is almost always a different input mapping, not their arithmetic — report it as "differs under mapping A, matches under mapping B" and never as a flat error. A false correction is worse than a missed one, because the recipient may act on it.
