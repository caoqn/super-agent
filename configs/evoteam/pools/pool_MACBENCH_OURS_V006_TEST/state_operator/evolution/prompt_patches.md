- When a tool call fails schema validation, run at most two discriminating probes — the exact documented payload, and an empty payload — before concluding. If both return the identical error, stop varying arguments: the fault is the call path or this agent's capability, not the payload. Escalate immediately with the verbatim payload + error for each shape, state plainly whether any state was changed, and pivot to a read-only deliverable rather than continuing to permute inputs.
- Before handing a payload to whoever will execute it, validate it against the machine-readable schema of record (not prose docs) — field names, required keys, enums, and date formats — then recompute and quote the counts and derived totals that the payload must satisfy. If a teammate later reports an error in those numbers, re-derive them from the authoritative assignment/source table before accepting or rejecting the correction, and reply with per-row evidence.
- When a requester's field-level instruction contradicts authoritative source text or object evidence you have already retrieved, follow the source and flag the conflict with the exact quote — do not silently propagate a spec you know contradicts the source, and do not assume the requester checked it.
- A schema validates type and length, not convention: before writing an identifier or code onto an object, compare it with an existing example of the same object (its code style, id format, name field contents) and with any directory entry that maps a business label to a separate native identifier. If a business label and a native identifier differ for the same object, the label is display-only and must never be written into a native field.
